Overview

This plan outlines a complete implementation for the Movie Watchlist assignment using Java and Spring Boot frameworks. The goal is to build a RESTful web application (MVC architecture) that integrates with external movie APIs (OMDb and TMDb), downloads movie images, and stores movie details in an H2 database. We will incorporate multi-threading (for parallel tasks) and Java Streams API for data processing. The solution will follow clear layering (controller, service, repository, model) in separate packages and adhere to best practices from the OOP3 course (clean code, frequent commits, testing, etc.). By following this step-by-step plan, a student can implement the project gradually and learn from each feature added.

External API Integration (OMDb and TMDb)

OMDb API (Movie Details): OMDb will provide detailed movie information by title. We will use the OMDb API (http://www.omdbapi.com) to fetch data like title, year, genre, director, plot, etc. The service layer should have a method to query OMDb given a movie title (and our API key). For example, a request URL might look like:
http://www.omdbapi.com/?t=<TITLE>&apikey=${OMDB_API_KEY}
(We will store the actual API key in application.properties and inject it into the service using @Value or @ConfigurationProperties, keeping the key out of code

.) The response is JSON; we can parse it using a JSON library (Jackson is included with Spring Boot). One approach is to define a small DTO or use a Map to extract needed fields. For instance, we might map the JSON to a Java record or class OmdbMovieResponse with fields like Title, Year, Genre, Director, Poster, etc. The service will call OMDb and populate our Movie entity with the returned data. If OMDb does not find the movie (e.g., returns "Response": "False"), the service should handle this gracefully – possibly throw a custom exception that the controller can catch and translate to a 404 Not Found response for the client. TMDb API (Images): TMDb will be used to fetch movie images. The plan is to download 3 images per movie and save them locally. We need an API key for TMDb as well (to be configured similarly in properties). The integration could work as follows:
Use TMDb Search API to find the movie and get its TMDb movie ID. For example, call GET https://api.themoviedb.org/3/search/movie?query=<TITLE>&api_key=${TMDB_API_KEY} which returns a JSON with a list of matching movies. Parse the first result to get the id and perhaps poster path.
Use TMDb Movie Details or Images API to get image paths. For instance, GET /3/movie/{movie_id}/images?api_key=... returns lists of posters and backdrop images. We can collect a few image URLs from here. The TMDb API typically provides image file paths which you combine with a base URL (e.g., https://image.tmdb.org/t/p/w500/<path> for a medium-size image). Alternatively, the search result often includes a poster_path – we could use that plus perhaps request a couple of backdrops via another endpoint.
Select 3 image URLs from TMDb results. For example, take the primary poster and the first two backdrops. The service will then download each of these images.
Downloading Images (I/O): To download an image from a URL, use Java's streaming I/O. We can use a URL object and open an InputStream to the image URL, then use an OutputStream to save to a file. For example, using a try-with-resources approach:
try (InputStream in = new URL(imageUrl).openStream();
     OutputStream out = new FileOutputStream(targetFile)) {
    in.transferTo(out); // Java 9+ method to copy streams 
}
This will read bytes from the URL and write them to a file. (Under the hood, this is similar to reading byte by byte in a loop and writing

For instance: images/711189_<movieId>_1.jpg, _2.jpg, _3.jpg. Storing images in an images/ directory within the project or in an external folder is fine; just ensure the path is configurable or documented. To keep track of these images, we have options:
Store the file paths in the Movie record (e.g., as a list of strings or a single concatenated string). This way, the information about where images are saved is in the database record.
Or rely on a convention (like images named by movie ID) and just document that convention. A simple approach is adding an imagePaths field to the Movie entity that joins the three filenames with commas or stores them in a JSON array.
Concurrency for API Calls and Downloads: Since network calls (to OMDb/TMDb) and image downloads are I/O-bound and can be slow, we will utilize multi-threading to speed up the process. Java 21 supports virtual threads, which are lightweight threads ideal for handling many I/O tasks in parallel
file-6kpi6lihvhr8wj47facwzu
. In the service’s "add movie" workflow, we can do the following concurrently:
Fetch movie details from OMDb.
Fetch image info from TMDb (search and/or details).
Download multiple images (three) in parallel.
For example, we can use an ExecutorService to submit tasks for each image download. Using a virtual thread executor is as simple as:
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
Future<?> img1 = executor.submit(() -> downloadImage(url1, file1));
Future<?> img2 = executor.submit(() -> downloadImage(url2, file2));
Future<?> img3 = executor.submit(() -> downloadImage(url3, file3));
// ... then wait for all to finish:
img1.get(); img2.get(); img3.get();
executor.shutdown();
This will download all three images in parallel, potentially making the "add movie" operation faster (roughly as fast as the slowest download, rather than sum of all three)
file-6kpi6lihvhr8wj47facwzu
. We could also parallelize the OMDb and TMDb requests if needed (submit them to the executor and wait), though OMDb is quick and usually one small JSON fetch. Virtual threads allow us to create many concurrent tasks without worrying about exhausting OS threads

file-6kpi6lihvhr8wj47facwzu

Mark the initial watched as false and no rating (or rating = 0) by default since it’s newly added. All sensitive data like API keys will be kept out of code and in application.properties. REST API Endpoints

We will expose a RESTful API for clients (or frontend) to interact with the watchlist. All endpoints will be under a common path like /api/movies (assuming we prefix with /api for clarity, though not strictly required). The controllers will be in the controller package, each annotated with @RestController. We’ll use meaningful request mappings and HTTP methods according to the operation (CRUD):
Add a Movie – POST /movies
This endpoint will add a new movie to the watchlist by querying the external APIs. The client can provide the movie title (and optionally year for precision) as input. For simplicity, the input can be a JSON body like { "title": "Inception" } or even just a query parameter ?title=Inception if we prefer. The controller method will accept the title, call the service’s add method, and return the created movie data (likely as a JSON of MovieDto). Upon success, return HTTP status 201 Created along with the movie data. If the movie is not found on OMDb (invalid title), return a 404 Not Found error. If the movie already exists in our DB (to prevent duplicates), we could return 409 Conflict or simply handle by either updating or ignoring – but this is an edge-case decision (for now, we can assume unique titles to simplify).
List Movies (Paginated) – GET /movies
Returns a paginated list of all movies in the watchlist database. Accept query parameters page and size for pagination (e.g. /movies?page=0&size=10). If not provided, default to page 0 and size 10 or 20. The controller will call the service or repository to retrieve the data. Using Spring Data JPA, for example, we get a Page<Movie> and then convert to a list of DTOs for output. The output JSON could include the list of movies and optionally pagination info (total count or next page link). Example response (JSON):
{
  "content": [ { "id":1, "title":"Inception", "year":2010, "watched":false, "rating":0, ...}, {...} ],
  "page": 0,
  "size": 10,
  "totalElements": 23,
  "totalPages": 3
}
If using our own pagination logic, just return the list for the requested page and perhaps the total count. This operation should return 200 OK always, with an empty list if no movies are stored.
Update Movie (Watched/Rating) – PUT /movies/{id} (or PATCH for partial update)
Allows updating the status of a movie in the watchlist – specifically marking it as watched and/or setting a rating. The client provides the movie id in the URL path and a JSON body with fields to update, e.g. { "watched": true, "rating": 5 }. The controller will map this to a DTO or directly to fields, then call the service to update. The service will fetch the Movie from the repository, apply the changes (with any necessary validation, like ensuring rating is 1–5), and save the entity. If the id is not found, return 404 Not Found. If the input is invalid (like rating 6), return 400 Bad Request. On success, return the updated movie data (status 200 OK). We choose PUT or PATCH semantics; since only two fields can be updated, either is fine – using PUT (full update) is acceptable as long as we document that only watched/rating are updatable.
Delete Movie – DELETE /movies/{id}
Removes a movie from the watchlist. The controller calls the service to delete the movie by id. If the movie doesn’t exist, return 404 Not Found; otherwise perform deletion. In the deletion process, we should also consider deleting the image files from disk so as not to leave orphaned files. The service can locate the saved image filenames (from the Movie record or by convention) and delete those files from the filesystem using the Java File API. After that, delete the database record via repository. Return 204 No Content on success (no response body needed).
All controller methods will be relatively thin: just handling HTTP specifics and delegating to service calls

@GetMapping("/movies") with @RequestParam page, size for listing.
@PutMapping("/movies/{id}") with @PathVariable id and @RequestBody for update.
@DeleteMapping("/movies/{id}") with @PathVariable for deletion.
We will also leverage Spring’s response handling: returning objects (or ResponseEntity) which Spring will auto-convert to JSON. If an exception occurs (like movie not found), we can throw a custom exception and use @ExceptionHandler or Spring’s ResponseStatusException to send an appropriate HTTP error status
file-g66woungtdgubvs8zh1tdb
file-g66woungtdgubvs8zh1tdb
